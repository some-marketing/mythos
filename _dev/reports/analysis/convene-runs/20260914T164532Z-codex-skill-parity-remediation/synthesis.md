# Convene synthesis

**Scope:** codex-skill-parity-remediation
**Origin:** codex
**Profile:** kernel (consequence-grade)
**Participants:** ALPHA/claude, NOW/codex, OMEGA/gemini

## Task

Adversarially review the proposed Codex skill parity remediation architecture before planning. Test canonical authority, alias behavior, capability honesty, framework-local exposure policy, validator choice, multi-actor custody, implementation slicing, and acceptance evidence.

## NOW / codex origin analysis

The audit establishes a genuine coverage problem, but it does not justify treating all missing paths as the same kind of defect. Canonical command pointers, direct system-skill packages, aliases, and framework-local helpers have different authority and discoverability properties. The first design was too broad because it proposed one additive generator before declaring those distinctions mechanically.

The safe architecture is one orchestration entry point with independently testable source-family strategies. Canonical command candidates must point to canonical authority at runtime and must not embed a selected subset of fields. Direct skills may be transformed from accepted Claude sources, preserving resources and recording the source hash. Aliases remain runtime resolutions; physical alias wrappers are not independent behavioral authorities. Framework-local helpers may be projected only under a collision-free namespace with their framework lineage and guardrails attached. Any source carrying harness-specific assumptions requires an explicit Codex override or remains `UNKNOWN` and unapplied.

Capability classification must come from registered runtime handlers and explicit adapter overrides, not a hand-maintained prose table. Presence, package validity, runtime resolution, semantic review, and blocking enforcement are separate evidence dimensions.

The current dirty tree prevents an undifferentiated refresh. The operator authorized the parity workstream, but that does not erase path-level ownership of concurrent untracked files. The plan may create proven-absent paths and change the explicitly adopted lifecycle/tooling files. Existing invalid or stale skill bodies must be handled in bounded batches that preserve content and have explicit custody evidence.

## Cross-verification catches

- Claude correctly found that the lifecycle capability table would reproduce drift unless it derives handler coverage mechanically. It also found that generated files need provenance metadata and source hashes, and that package validation alone does not prove real Codex discoverability.
- Gemini correctly challenged the assumption that framework entry routing alone provides granular helper access. The plan will support collision-free framework-local candidate projection, but will stage these candidates until their lineage and semantic classification pass.
- Gemini's recommendation to overwrite every invalid skill is rejected. Invalid packaging is evidence for repair, not authority to replace foreign work in a multi-actor tree.
- Both reviewers challenged physical alias duplication. Alias parity will be tested through the runtime resolver and catalog descriptions; aliases will not acquire independent behavior.
- Philosophy grounding independently found a concrete negative fixture: `ground-in-philosophy` contains Pi-specific semantics. That disproves bulk canonical auto-application and requires per-command classification or adapter override.

## Net findings

The architecture is viable only after six adjustments:

1. Add a probationary evidence step for the existing lifecycle projector before generalization.
2. Drive capability classification from the real handler registry plus explicit adapter overrides.
3. Stamp every generated candidate with generator identity, source path, source hash, projection kind, capability tier, and review state.
4. Stage `UNKNOWN` or harness-specific candidates and block their application until reviewed.
5. Resolve aliases dynamically and verify them mechanically instead of cloning target behavior into alias files.
6. Require both negative fixtures and real-harness receipts; file presence and schema validity are not semantic parity.

The plan is BIG because it changes cross-harness discovery and potentially many files. Execution must therefore use bounded worker slices, retain the consequence-grade convene evidence, and end in distinct-family acceptance review. No `instructions/canonical/**` mutation is authorized by this plan.
