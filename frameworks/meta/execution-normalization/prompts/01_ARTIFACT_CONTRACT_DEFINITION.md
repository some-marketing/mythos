# 01 — Artifact Contract Definition

> **Type**: Atomic
> **Mode**: REVIEW_ONLY — reads framework files, writes analysis artifacts to `docs/`. Never modifies source files, framework definitions, or prompt files.
> **Purpose**: Inventory every artifact type in the target framework, define canonical schemas for each, and document the gap between the current state and a fully specified contract. The output is a durable reference that subsequent prompts and verification scripts depend on.

---

## Prerequisites

Read `00_SHARED_DEFINITIONS.md` before executing this prompt. All capitalized terms used below are defined there.

---

## Inputs

| Input | Required | Description |
|-------|----------|-------------|
| `FRAMEWORK_ID` | Yes | Identifier of the target framework (see `00_SHARED_DEFINITIONS.md#standard-input-variables`) |
| `PROJECT_ROOT` | Yes | Absolute path to the workspace root |
| Framework manifest | Yes | The `manifest.json` at `frameworks/{FRAMEWORK_ID}/manifest.json` |
| Existing framework docs | No | Any `.md` files under `frameworks/{FRAMEWORK_ID}/docs/` |
| Existing prompt files | Yes | All `.md` files under `frameworks/{FRAMEWORK_ID}/prompts/` |

---

## Process

### Step 1: Read the Target Framework [AUTO]

1. Locate the framework at `frameworks/{FRAMEWORK_ID}/`.
2. Read `manifest.json`. Record: prompt count, declared modes, declared MCP requirements, any schema references.
3. Read all prompt files under `prompts/`. For each prompt, note: inputs declared, outputs declared, artifact names referenced (by path pattern or by name).
4. Read all files under `docs/` if the directory exists. Note: any artifact described, any schema referenced, any naming convention stated.
5. If `manifest.json` does not exist, STOP and report: `FRAMEWORK_ID` resolves to a path that has no manifest. Request the correct framework identifier.

### Step 2: Inventory All Artifact Types [AUTO]

Using the content collected in Step 1, identify every distinct artifact type. An artifact type is a named category of file — not an individual file instance.

For each artifact type discovered, record:

| Field | Description |
|-------|-------------|
| `name` | Canonical name for this artifact type |
| `path_pattern` | Path template or glob (e.g., `outputs/runs/{RUN_ID}/summary.json`) |
| `data_format` | Prose, structured data, or binary (do not name specific file formats) |
| `lifecycle_stage` | `input`, `intermediate`, `derived`, or `archived` |
| `ownership` | `framework` (defined and controlled by the framework) or `project` (produced per run or per project instance) |
| `mutability` | `immutable` (written once, never overwritten) or `mutable` (may be updated across runs or iterations) |
| `producing_prompt` | Which prompt(s) write this artifact (by prompt filename) |
| `consuming_prompts` | Which prompt(s) read this artifact as input |

Classify artifact types into these categories:

- **Input artifacts**: consumed but not produced by the framework (supplied by the caller)
- **Output artifacts**: produced as final deliverables for downstream consumers
- **Intermediate artifacts**: produced and consumed within the same pipeline run
- **Derived artifacts**: generated by processing other artifacts (reports, summaries, diffs)
- **Archived artifacts**: retained for audit or replay purposes but not actively consumed

An artifact type may belong to more than one category.

### Step 3: Confirm Inventory Completeness [USER]

Present the artifact inventory as a structured list grouped by lifecycle stage. Ask the framework author:

1. Are there artifact types that the framework produces or consumes that are not in this list?
2. Are any of the lifecycle stage or ownership classifications incorrect?
3. Are there artifact types planned for future prompts that should be included now?

**STOP and wait for user response. Do not proceed until the inventory is confirmed or corrections are received.**

If the user confirms without changes, proceed. If the user provides corrections, update the inventory before proceeding.

### Step 4: Define Canonical Naming Rules [AUTO]

For each artifact type in the confirmed inventory, define:

1. **Canonical name**: a stable, human-readable identifier for this artifact type (snake_case recommended)
2. **Path template**: the full path pattern relative to `PROJECT_ROOT`, using `{VARIABLE}` placeholders for dynamic segments
3. **Identity fields**: the minimum set of fields (or path segments) that uniquely identify one instance of this artifact type within a run or project

Document any naming conventions that apply across multiple artifact types (e.g., all intermediate artifacts share a common path prefix, all final reports follow a naming pattern).

### Step 5: Document Schema Stability Constraints [AUTO]

For each artifact type, classify its fields into two groups:

- **Frozen fields**: fields that, once defined, must not be renamed, removed, or have their type changed without a versioning increment. These are the fields that downstream consumers and verification scripts depend on.
- **Evolving fields**: fields that may be added, renamed, or removed as the framework matures without breaking compatibility.

State the basis for each classification: cite the prompt or downstream consumer that depends on a field being stable.

If an artifact type has no schema yet (i.e., it exists informally as files produced by the framework but with no schema document), record its frozen fields as `[undetermined — schema not yet defined]` and flag it in the gap report.

### Step 6: Produce Gap Report [AUTO]

Identify gaps between the current state of the framework and a fully specified contract. A gap is any of the following conditions:

| Gap Type | Description |
|----------|-------------|
| `missing_schema` | Artifact type exists and is produced/consumed, but has no schema document |
| `unenforced_schema` | Schema document exists but no verification script checks instances against it |
| `undocumented_artifact` | Framework produces files that are not declared in any prompt's output section |
| `missing_producer` | Artifact type is declared as an input in a prompt but no prompt in this framework produces it |
| `missing_consumer` | Artifact type is produced but no downstream prompt or external system is documented as consuming it |
| `naming_inconsistency` | The same artifact type is referred to by different names in different prompts |

For each gap, record:
- Gap type (from the table above)
- Affected artifact type(s)
- Evidence: file path and prompt or section where the gap was observed
- Severity: CRITICAL (blocks execution), MAJOR (causes ambiguity), MINOR (cosmetic or documentation-only)

### Step 7: Write ARTIFACT_CONTRACT.md [AUTO]

Write `docs/ARTIFACT_CONTRACT.md` at `PROJECT_ROOT`. The document must contain these sections in order:

```markdown
# Artifact Contract — {FRAMEWORK_ID}

## Overview
- Framework: {FRAMEWORK_ID}
- Contract version: 1.0
- Generated: {ISO-8601 date}
- Total artifact types: {exact integer}

## Artifact Inventory

### Input Artifacts
[One subsection per artifact type, with: canonical name, path template, data format,
 ownership, mutability, consuming prompts, identity fields]

### Output Artifacts
[Same structure]

### Intermediate Artifacts
[Same structure]

### Derived Artifacts
[Same structure]

### Archived Artifacts
[Same structure]

## Naming Conventions

```

If the gap report contains any findings, also write `docs/ARTIFACT_CONTRACT_GAP_REPORT.md`. The gap report must contain:

---

## Success Criteria

- Framework manifest located and read without error
- All prompt files read; all declared inputs and outputs captured
- Artifact inventory confirmed by framework author
- Every artifact type has: canonical name, path template, lifecycle stage, ownership, mutability
- Schema stability classification recorded for each artifact type
- All gap types checked; gaps documented with evidence citations
- `ARTIFACT_CONTRACT.md` written with all required sections
- Gap report written if and only if gaps were found
- No forbidden labels per `guardrails.md` in any written document
- All evidence citations use `path/to/file:section` format

---

## Failure Modes

| Condition | Action |
|-----------|--------|
| `manifest.json` not found at `frameworks/{FRAMEWORK_ID}/` | STOP; report path checked and request correct `FRAMEWORK_ID` |
| No prompt files found under `prompts/` | STOP; report that the framework appears to have no prompts; request confirmation before proceeding |
| Framework author does not respond to Step 3 confirmation | Do not proceed; leave the process paused at Step 3 |
| Artifact type cannot be classified into any lifecycle stage | Record as `lifecycle_stage: unclassified`; flag in gap report as MINOR |
| Two prompts declare conflicting paths for the same artifact type | Record as a `naming_inconsistency` gap with MAJOR severity; do not resolve the conflict — flag for human review |
| Gap report would be empty | Do not write `ARTIFACT_CONTRACT_GAP_REPORT.md`; note in `ARTIFACT_CONTRACT.md` that no gaps were detected |

## Graduation Path

| Level | What changes |
|-------|-------------|
| L0 | LLM reads all framework files and produces `ARTIFACT_CONTRACT.md` from scratch. No schema files exist. Gap report is written based on LLM observation alone. |
| L1 | A verification script checks that `ARTIFACT_CONTRACT.md` exists and contains all required sections (Overview, Artifact Inventory, Naming Conventions, Schema Stability Constraints). Script gates on section presence, not content correctness. |
| L2 | Schema files exist for each artifact type listed in the contract. Verification validates schema file presence and validates at least one real artifact instance against each schema. LLM fills descriptions and stability annotations. |
| L3 | A script auto-generates the artifact inventory by scanning the manifest and prompt files for declared inputs/outputs. LLM fills descriptions, stability annotations, and gap analysis. Human reviews the generated inventory before the contract is written. |
| L4 | Fully mechanical: inventory generation, schema validation, and gap detection all run as code. LLM is invoked only when a new artifact type appears in the framework that no existing rule or schema can classify. |

## Binding Points

| Name | Description |
|------|-------------|
| `FRAMEWORK_DIR` | Absolute path to the root of the target framework (e.g., `frameworks/wordpress/qa`). Used in Step 1 to locate the manifest and prompt files. |
| `ARTIFACT_TYPES (discovered)` | The list of artifact type names produced by Step 2. This value is not supplied up front — it is derived by running this prompt. It becomes the input to subsequent prompts that need to enumerate artifact types. |
| `SCHEMA_DIR` | The directory where schema files for this framework's artifact types are stored (e.g., `schemas/`). Used in Steps 5 and 6 to check for existing schema files. If no schema directory exists yet, record as absent and flag in the gap report. |
